# Android — In-App Messaging (IAM)

Available from Android SDK **`1.0.0`** (the pinned baseline in `version-matrix.md`; `0.1.0` and earlier have no IAM API). Cross-platform semantics — triggers, audience, action types, frequency caps, troubleshooting — live in `../pushengage/in-app-messaging.md`; read that first if the customer's question is about *behavior* rather than Android code.

## What IAM needs on Android

**Nothing beyond the existing push integration.** IAM activates inside `PushEngage.Builder().…build()` when an App ID is set.

| Item | Required? | Notes |
|---|---|---|
| `com.github.awesomemotive:pushengage-android-sdk:1.0.0` | Yes | Same coordinate as push (`install.md`). No new dependency — IAM reuses the SDK's bundled Room / WorkManager / OkHttp. |
| `Builder().addContext(...).setAppId(...).build()` in `Application.onCreate()` | Yes (already part of push) | Must be the `Application` class, not an Activity, so the SDK's activity-lifecycle callbacks see the first `onResume`. |
| Manifest entries / permissions / `<queries>` | No | The SDK's own library manifest adds an internal `<provider>` (activity tracker) that manifest merger brings in automatically; the host adds nothing. |
| ProGuard / R8 rules | No | `1.0.0` ships consumer rules inside the AAR (Gson models, Retrofit interfaces, the WebView `@JavascriptInterface`), so minified release builds work with no host configuration. |
| Activity lifecycle forwarding, `onRequestPermissionsResult` forwarding, `android:configChanges` | No | The SDK registers `ActivityLifecycleCallbacks` itself, handles rotation without re-counting the impression, and receives the permission result from its own fragment / helper activity (ANDROID-BP-17). |
| Push subscription / notification permission | No | IAM syncs and displays without either. |

Compose vs Views: no separate path. The message is a `FrameLayout` + `WebView` attached to the activity's content view, identical for `ComponentActivity` (Compose) and classic Activities. Only the `request_notification_permission` button branches: `ComponentActivity` hosts use an internal fragment; plain `Activity` hosts use an invisible helper activity. (`PushEngage.requestNotificationPermission(...)` itself still requires `ComponentActivity` — ANDROID-BP-01 is unchanged.)

## API

Three public methods (one with overloads) and one interface. Everything else under `com.pushengage.pushengage.iam.*` is internal or `@RestrictTo` — never reference it (ANDROID-BP-17).

### `triggerIAMEvent` — report a custom trigger event

```kotlin
// Simplest form
PushEngage.triggerIAMEvent("app_launched")

// With parameters
PushEngage.triggerIAMEvent(
    "cart_abandoned",
    mapOf("cart_value" to 120, "currency" to "USD")
)

// With a callback
PushEngage.triggerIAMEvent("cart_abandoned", params, object : PushEngageResponseCallback {
    override fun onSuccess(response: Any?) { /* event accepted */ }
    override fun onFailure(errorCode: Int?, errorMessage: String?) { /* e.g. 400 Event name is required */ }
})
```

```java
// Simplest form
PushEngage.triggerIAMEvent("app_launched");

// With parameters and a callback
Map<String, Object> parameters = new HashMap<>();
parameters.put("cart_value", 120);
parameters.put("currency", "USD");

PushEngage.triggerIAMEvent("cart_abandoned", parameters, new PushEngageResponseCallback() {
    @Override
    public void onSuccess(Object responseObject) { }

    @Override
    public void onFailure(Integer errorCode, String errorMessage) { }
});
```

- Overloads: `triggerIAMEvent(String)`, `triggerIAMEvent(String, Map<String, Object>)`, `triggerIAMEvent(String, Map<String, Object>, PushEngageResponseCallback)`. Pass `null` for `parameters` if not needed.
- `PushEngageResponseCallback` has two abstract methods, so Kotlin needs an `object :` expression (same as `getSubscriberId`).
- `onSuccess(null)` means the event was **accepted**, not that a message was displayed. Blank name → `onFailure(400, "Event name is required")`.
- Deliberately **not** gated on subscription, permission, or site status — safe to call anywhere after `build()`.
- Values are stringified before matching (`120` and `120.0` both become `"120"`); have the dashboard condition typed `number` for numeric comparisons (XP-BP-08).
- Campaigns with an **app open** trigger need no call — the SDK fires them once per process.

### `setIAMCustomActionHandler` — receive `custom` button taps

```kotlin
import com.pushengage.pushengage.iam.action.IAMCustomActionHandler

PushEngage.setIAMCustomActionHandler(object : IAMCustomActionHandler {
    override fun onCustomAction(actionId: String, parameters: Map<String, Any>) {
        // parameters["action"] is the button's "Action name" from the dashboard — route on it.
        // actionId is the button's internal key (e.g. "t04B05"), generated by the dashboard.
        when (parameters["action"]) {
            "view_cart" -> navigateToCart()
            "apply_coupon" -> applyCoupon(parameters["code"]?.toString())
        }
    }
})
```

```java
import com.pushengage.pushengage.iam.action.IAMCustomActionHandler;

PushEngage.setIAMCustomActionHandler((actionId, parameters) -> {
    // parameters.get("action") is the dashboard Action name — route on it, not on actionId.
    switch (String.valueOf(parameters.get("action"))) {
        case "view_cart":
            navigateToCart();
            break;
        case "apply_coupon":
            applyCoupon(String.valueOf(parameters.get("code")));
            break;
    }
});
```

- Interface: `com.pushengage.pushengage.iam.action.IAMCustomActionHandler` with `fun onCustomAction(actionId: String, parameters: Map<String, Any>)`. It is a plain Kotlin `interface`, **not** a `fun interface` — a Kotlin lambda (`setIAMCustomActionHandler { … }`) does not compile; use `object :` (ANDROID-BP-18 / KI-A008). Java lambdas work.
- **Route on `parameters["action"]`** — the button's Action name from the dashboard. `actionId` is a dashboard-generated internal key (e.g. `"t04B05"`); never switch on it.
- Scalar `parameters` values arrive as `String`s (matching iOS); nested objects/arrays pass through as-is.
- Called on the UI thread. `null` clears the handler.
- May be registered **before** `Builder.build()` — the SDK stashes it and applies it once IAM is ready.
- **Register once, app-wide, in `Application.onCreate()`** (ANDROID-BP-16). Campaigns with `custom` buttons can display on any screen; a handler registered only inside one Activity leaves taps unhandled elsewhere (the SDK logs `No custom action handler set`, still counts the click, still dismisses).
- Only `custom` buttons arrive here. `open_url` (http/https only, opened externally), `dismiss`, and `request_notification_permission` are SDK-handled. A `url` parameter on a `custom` action is **not** opened for you — for in-app navigation / custom-scheme deep links, put the route in a parameter and navigate here (XP-BP-09).

Where it goes in the `init-code.md` template (diff + confirm posture — Application class):

```kotlin
class PEApplication : Application() {
    override fun onCreate() {
        super.onCreate()

        if (BuildConfig.DEBUG) {
            PushEngage.enableLogging(true)   // before build() so IAM init is logged
        }

        // App-wide IAM custom-action handler (may precede build()).
        PushEngage.setIAMCustomActionHandler(object : IAMCustomActionHandler {
            override fun onCustomAction(actionId: String, parameters: Map<String, Any>) {
                // route on parameters["action"] (dashboard Action name), not actionId
            }
        })

        PushEngage.Builder()
            .addContext(applicationContext)
            .setAppId("APP_ID_FROM_DASHBOARD")
            .build()

        PushEngage.setSmallIconResource("ic_pushengage_notification")
    }
}
```

Only add the handler block if the customer's campaigns use (or will use) `custom` buttons. Don't add `triggerIAMEvent` calls to `onCreate` — they belong at the product moments the campaigns key off.

## Verification

1. Customer creates and publishes an **app-open** campaign (any position, with a Dismiss button) on the dashboard.
2. Install a debug build with `enableLogging(true)` on a device or emulator (IAM does not need Google Play Services or FCM, so any emulator image works for this step).
3. **Force-stop and relaunch** the app (app-open fires once per process — backgrounding is not enough).
4. The message appears; tapping Dismiss closes it. `adb logcat -s PushEngage` shows `Eligible message: <id>, priority: N`.
5. For a custom-trigger campaign: call `triggerIAMEvent("<exact dashboard event>")` from a debug button; logcat shows `Found N eligible messages for: <event>` (or `No messages found for trigger: …`).

If nothing appears → `../pushengage-debug/diagnostic-tree.md` Branch 8, with the logcat rejection lines (`../pushengage-debug/log-readers.md` → In-App Messaging).

## Android gotchas

- **App-open fires once per process.** Returning from background does not re-show; only a fresh process does.
- **Backgrounding dismisses a displayed message** and it still counts against the frequency cap. Rotation does not (the SDK re-attaches without re-counting).
- **Periodic sync uses WorkManager** (~6 h, network-constrained). If the host app disabled WorkManager's default initializer without providing its own, the SDK logs a scheduling failure and only syncs on app open — IAM still works, just refreshes less often.
- **`enableLogging(true)` before `build()`** to see IAM init logs, including the `IAM Database Summary` dump of synced campaigns.
- **Swipe-to-dismiss** applies to `center` modals only (not banners), and only when the campaign enables tap-to-dismiss.
- **`open_url` refuses non-http(s) schemes** (`myapp://…` does nothing except log and dismiss) — KI-A009.
- **Subscriber-data audience rules** (segments, `attr.*`, geo) stay deferred until the device is a push subscriber; device-data rules work everywhere.
- Room schema migrates 1→2 automatically on upgrade from a pre-IAM SDK; no host action.

## Edit posture

- `Application` subclass edits (handler registration) — diff + confirm.
- `triggerIAMEvent` call sites in Activities/ViewModels — diff + confirm.
- No config-file edits are needed for IAM. Don't add manifest entries, `configChanges`, or ProGuard rules "for IAM" — the SDK ships its own consumer rules and merges its own manifest additions.
