# PushEngage Concepts (terminology reference)

Use this when a customer mentions a PushEngage term and you are not 100% sure what it means. Do not guess. If a term is not here and the customer is using it loadbearing, ask the customer or fetch the docs.

## Site

The container for a customer's PushEngage configuration. One site per app, per environment (e.g., a separate test/QA site and production site).

## App ID (UUID)

A UUID generated by PushEngage when the customer creates a site/app in the dashboard. Example (fake): `00000000-1111-2222-3333-444444444444`. The customer pastes this into their app code via `PushEngage.setAppID(id: "…")` (iOS) and equivalent methods on other platforms.

**Not to be confused with "App Push Id"** — see below.

## App Push Id (iOS)

On the iOS SDK dashboard tab specifically, "App Push Id" is the customer's **iOS Bundle Identifier** (e.g. `com.example.MyApp`). The dashboard asks for it to match incoming APNs traffic to the customer's site. The customer enters this; PushEngage does not generate it.

**These are two distinct values on the same dashboard page:**

| Field on dashboard | Value | Who provides | Used where |
|---|---|---|---|
| App Push Id | iOS Bundle Identifier | Customer enters | Dashboard config |
| App ID | UUID | PushEngage generates | Customer copies, pastes into `setAppID(id:)` (iOS) / `setAppId(...)` elsewhere |

When a customer says "App ID," ask which one if it's ambiguous.

## Subscriber

A device + app install paired with PushEngage. Subscribers are created when the SDK successfully registers an APNs (or FCM) token with PushEngage's servers. A single user with two devices = two subscribers.

## Subscriber Hash / Device Token Hash

A hashed identifier the SDK uses internally. Treat as PII — don't log raw, don't store outside the SDK's own storage.

## Profile ID

An optional customer-side identifier the app can attach to a subscriber (e.g., the customer's own user ID). Allows merging multiple device subscribers under one user.

## Segment

A named group of subscribers. Segments can be static (the app calls `addSegment(...)`; the iOS SDK names it `addSegments(...)`) or dynamic (rule-based on the dashboard side).

## Tags / Subscriber Attributes

Key-value pairs attached to a subscriber for targeting (e.g., `plan=premium`, `city=Berlin`). Different SDKs use slightly different APIs (`addSubscriberAttributes`, `setSubscriberAttributes`).

## Goal

A custom conversion event the app reports back to PushEngage for campaign attribution. Has a name, count (integer), and value (number).

## Trigger Campaign / Triggered Notification

A campaign configured on the dashboard that fires when the app reports a matching event via `sendTriggerEvent`. Different from broadcast notifications (which are scheduled or manual sends from the dashboard).

## Custom Event (trackEvent)

A named analytics event the app reports via `trackEvent(...)` to start or exit dashboard automation workflows. Distinct from a Goal (conversion attribution) and from a Trigger Campaign event: a custom event carries an `eventName` plus optional `data`, and the SDK defaults its `provider` to `"PushEngage"` and `eventType` to `"PushEngage.CustomEvent"` when omitted. Added across all platforms in the current SDK generation (iOS `0.1.0`, Android `0.1.0`, Flutter `1.0.0`, React Native `1.0.0`).

## User Identification (identify / logout)

A way to attach known personal fields to a subscriber via `identify(...)` and remove them via `logout(...)`. Only **12 predefined fields** are accepted: `first_name`, `last_name`, `email`, `phone`, `gender`, `dob`, `language`, `profile_id`, `country`, `city`, `state`, `zip`. Arbitrary keys are rejected — use Subscriber Attributes (tags) for custom key-values instead. `logout` with no field list clears the default PII set (`first_name, last_name, email, phone, gender, dob, profile_id`). All `identify` values are PII — treat as sensitive (don't log in release builds). Added across all platforms in the current SDK generation.

## Badge Count

The numeric badge on the app icon. `setBadgeCount(n)` sets it; `setBadgeCount(0)` clears it. On iOS the SDK uses the iOS 16+ badge API with a pre-16 fallback; on Android the count applies to subsequent notifications (Android has no system numeric launcher badge). Invalid inputs (NaN/∞/out-of-range) are coerced to `0` (cleared).

## Alert (Price Drop / Back-in-Stock)

A subscription-style alert tied to a specific product. The app calls `addAlert(...)` with a product reference, price, availability, etc. When dashboard-side conditions match (price drops, item restocked), PushEngage notifies the subscriber.

## Notification Service Extension (NSE) — iOS only

An iOS app extension target that runs before a notification is displayed. PushEngage uses it to attach rich media (images), handle mutable content, and ensure tracking fires. Required for rich notifications. See the iOS spoke for setup.

## Notification Content Extension (NCE) — iOS only

A separate iOS app extension that renders a custom expanded notification UI. Optional. Notifications still deliver without it, but the customer's custom layout (if any) won't be shown — iOS falls back to its default expanded view.

## App Group — iOS only

An Apple-specific capability that lets the main app and its extensions share data. PushEngage requires one for NSE ↔ main app communication. The shared group identifier goes into both Info.plist files under the key `PushEngage_App_Group_Key`.

## Method Swizzling — iOS only

A runtime mechanism where the SDK replaces the customer's `UIApplicationDelegate` / `UNUserNotificationCenterDelegate` methods with PushEngage-aware ones. Enabled by `PushEngage.swizzleInjection(isEnabled: true)`. Default and recommended. Disabled when another SDK also swizzles (e.g., Firebase Messaging with default config) or when the customer's policy disallows runtime swizzling — in which case the customer must wire four delegate methods manually. See the iOS spoke.

## Auto Handle Deeplink — iOS only

An Info.plist flag (`PushEngageAutoHandleDeeplinkURL`) that controls whether the SDK auto-opens URLs received in notifications. Defaults to `false` in the SDK — http URLs are NOT auto-opened unless the flag is set to `YES`. A common source of "deep link doesn't work" customer reports.

## Sandbox vs Production APNs

Apple distinguishes development push tokens (sandbox) from App Store / TestFlight push tokens (production). PushEngage's APNs cert (Apple Push Notification service SSL — Sandbox & Production) covers both in a single cert, so customers don't have to upload two.
