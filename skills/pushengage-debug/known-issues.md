# PushEngage Known Issues — Version Pinned

Each row is a confirmed issue. Match the customer's SDK version against `affected_versions` first; report only when a hit exists.

> **Pinned baselines (2026-08):** iOS native `1.0.0` (two-pod split: `PushEngage` + `PushEngageExtension`), Android native `0.1.0`, Flutter plugin `1.0.0` (transitive iOS `PushEngage`/`PushEngageExtension` `1.0.0` + Android `0.1.0`), React Native plugin `1.0.1` (maintenance release over `1.0.0` — wrapper-version bump + codegen typing fix, no behavior change; transitive iOS `1.0.0` + Android `0.1.0` unchanged). Rows below are scoped to these baselines.

## How to use this file

Read it. For each row:

- If the customer's SDK version falls in `affected_versions` AND the symptom matches what they reported → present the row to them as a match.
- If they're on a newer version that's in the `fixed in` column → tell them they're already on a fixed version; the bug they're seeing is something else.

When proposing the fix, explain the cause plainly so the customer knows exactly what to change.

---

When an SDK releases a new version, this file must be updated:

1. Add new rows for newly discovered issues.
2. Update `fixed in` columns for rows resolved in the new version.
3. Bump the affected `version-matrix.md` in the platform spoke(s).
4. Re-run audit and symptom-tree tests against the new version.
5. For native version bumps that the Flutter/RN wrappers consume transitively, re-check the `(transitive)` version references in the KI-F0xx / KI-RN0xx rows.
