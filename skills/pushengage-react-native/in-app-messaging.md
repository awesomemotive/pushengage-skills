# React Native — In-App Messaging (IAM)

Available from `@pushengage/pushengage-react-native` **`1.1.0`** (the pinned baseline in `version-matrix.md`; transitive natives iOS `PushEngage 1.1.0` / Android `1.0.0`). Cross-platform semantics — triggers, audience, action types, frequency caps, troubleshooting — live in `../pushengage/in-app-messaging.md`; read that first if the customer's question is about *behavior* rather than JS code.

## What IAM needs in an RN app

| Item | Required? | Notes |
|---|---|---|
| `"@pushengage/pushengage-react-native": "^1.1.0"` + `npm install` + `cd ios && pod install` | Yes | `1.0.x` has no IAM API (`PushEngage.triggerIAMEvent is not a function`). RN ≥ 0.78 unchanged. |
| `PushEngage.setAppId(...)` in `index.js` | Yes (already part of push) | IAM syncs as soon as the App ID is set. No push subscription, no permission. |
| iOS deployment target | Already satisfied | The native pod now needs iOS 15.0; RN 0.78's floor is 15.1, so nothing to change. |
| Android: manifest / `MainActivity` / `MainApplication` changes | No | None. The module hands the already-resumed activity to the SDK itself. Do NOT forward `onRequestPermissionsResult`. |
| iOS: `AppDelegate` changes | No | The module wires the native custom-action callback on init. Don't call `setIAMCustomActionHandler` from native code — it would overwrite the module's handler and `onIAMCustomAction` would go silent. |
| JS activation call | No | The native custom-action forwarder is enabled automatically on module load. `setIAMCustomActionHandlerEnabled` is internal and **not** on the `PushEngage` object (RN-BP-15 / KI-RN015). |
| iOS optional: `BGTaskSchedulerPermittedIdentifiers` = `com.pushengage.iam.refresh` in `ios/<App>/Info.plist` + Background Modes → Background fetch | Optional | Background campaign refresh. Both or neither; without them campaigns refresh on app open. Android needs nothing. |
| Expo | Same as push | No config plugin exists; Expo Go can't load the module. Bare / `expo prebuild` with `expo-dev-client`. The optional Info.plist key goes in `app.json` → `ios.infoPlist` (and `UIBackgroundModes: ["fetch"]`) before prebuild. |

## API

Two members plus one exported type.

### `triggerIAMEvent` — report a custom trigger event

```tsx
try {
  await PushEngage.triggerIAMEvent('cart_abandoned', {
    cart_value: 120,
    currency: 'USD',
  });
} catch (e) {
  // e.code === '400' && e.message === 'Event name is required' for a blank name
}
```

- Signature: `triggerIAMEvent(eventName: string, parameters?: { [key: string]: string | number | boolean }): Promise<string | null>`. Omitted `parameters` is coerced to `null` for the codegen boundary by the wrapper — don't do it yourself.
- Resolves with the native message (`"In-app message event triggered successfully"`). Resolution means the event was **accepted**, not that a message was displayed. Rejects (plain `Error` with string `.code` / `.message`) on a blank name or a native failure — wrap in `try/catch`.
- Values are stringified natively before matching (`2` matches a condition authored as `2`); Android silently drops `null` values. Have numeric dashboard conditions typed `number` (XP-BP-08).
- Campaigns with an **app open** trigger need no call — the native SDK fires them once per process.

### `onIAMCustomAction` — receive `custom` button taps

In the root component, alongside the push listeners from `init-code.md`:

```tsx
import React from 'react';
import type { EventSubscription } from 'react-native';
import PushEngage, { type IAMCustomAction } from '@pushengage/pushengage-react-native';

export default function App() {
  React.useEffect(() => {
    const pushSub: EventSubscription = PushEngage.onValueChanged(handleDeepLink); // push taps
    PushEngage.getInitialNotification().then(handleColdBoot);

    const iamSub: EventSubscription = PushEngage.onIAMCustomAction(
      ({ actionId, parameters }: IAMCustomAction) => {
        // parameters.action is the button's "Action name" from the dashboard — route on it.
        // actionId is the button's internal key (e.g. "t04B05"), generated by the dashboard.
        switch (parameters.action) {
          case 'view_cart':
            navigation.navigate('Cart');
            break;
          case 'apply_coupon':
            applyCoupon(parameters.code);
            break;
        }
      },
    );

    return () => {
      iamSub.remove();   // RN-BP-14
      pushSub.remove();  // RN-BP-08
    };
  }, []);

  return /* ... */;
}
```

- `PushEngage.onIAMCustomAction(callback)` returns an `EventSubscription`; call `.remove()` in the effect cleanup (RN-BP-14).
- `IAMCustomAction` (exported type): `{ actionId: string; parameters: { [key: string]: string } }` — values are always strings. **Route on `parameters.action`** (the dashboard Action name); `actionId` is a dashboard-generated internal key — never switch on it.
- No activation step. Unlike push taps there is **no cold-boot buffering** — by design, a button tap can't happen before JS is up — so timing is lifecycle hygiene, not a correctness issue.
- Only `custom` buttons arrive here. `open_url` (http/https only, opened externally), `dismiss`, and `request_notification_permission` are handled natively. A `url` parameter on a `custom` action is **not** opened for you — for in-app navigation, put the route in a parameter and navigate here (XP-BP-09). IAM taps never arrive on `onValueChanged` or `getInitialNotification`.
- Nothing subscribed → the tap still counts as a click and the message still closes.

## Verification

1. Customer creates and publishes an **app-open** campaign (with a Dismiss button) on the dashboard for the platform's site (one site per platform — the App ID passed to `setAppId` decides which campaigns sync).
2. Run a debug build with `if (__DEV__) PushEngage.enableLogging(true)`. iOS simulator is fine — IAM does not need APNs; an Android emulator without Play Services is fine too.
3. **Force-quit and relaunch** (app-open fires once per process).
4. The message appears; Dismiss closes it.
5. For a custom-trigger campaign: call `triggerIAMEvent('<exact dashboard event>')` from a debug button and watch the native logs (Xcode console / `adb logcat -s PushEngage`) for the eligibility lines. The RN module adds no JS-side log of its own.

If nothing appears → run `audit-checks.md` (RN-AUDIT-19/20), then `../pushengage-debug/diagnostic-tree.md` Branch 8 with the native rejection lines (`../pushengage-debug/log-readers.md` → In-App Messaging).

## RN gotchas

- **Two sites, two campaign sets.** A cross-platform app has separate iOS and Android sites; a campaign published on one does not show on the other platform.
- **`^1.1.0` is the floor.** A stale lockfile on `1.0.1` leaves `PushEngage.triggerIAMEvent` undefined.
- **`pod install` after the bump**, as always (RN-BP-09).
- **Never call `PushEngage.setIAMCustomActionHandlerEnabled(...)` or `getIAMDatabaseState()`** — the first is internal-only (throws `undefined is not a function`), the second never shipped (KI-RN015).
- **Success ≠ shown.** A resolved promise means the event was accepted; display depends on sync, trigger match, date window, cap and audience.
- **App-open fires once per process**, on both platforms.
- **Subscriber-data audience rules** need a push subscription; device-data rules work everywhere.

## Edit posture

- `package.json`, `ios/<App>/Info.plist` — auto-edit + announce.
- Background fetch capability — customer-driven (Xcode UI).
- Root `App.tsx` (subscription) and `triggerIAMEvent` call sites — diff + confirm.
- Do NOT touch `AppDelegate.swift`/`.mm`, `MainActivity.kt`, `MainApplication.kt`, or `AndroidManifest.xml` for IAM.
