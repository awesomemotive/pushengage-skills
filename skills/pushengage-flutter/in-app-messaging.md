# Flutter — In-App Messaging (IAM)

Available from `pushengage_flutter_sdk` **`1.1.0`** (the pinned baseline in `version-matrix.md`; transitive natives iOS `PushEngage 1.1.0` / Android `1.0.0`). Cross-platform semantics — triggers, audience, action types, frequency caps, troubleshooting — live in `../pushengage/in-app-messaging.md`; read that first if the customer's question is about *behavior* rather than Dart code.

## What IAM needs in a Flutter app

| Item | Required? | Notes |
|---|---|---|
| `pushengage_flutter_sdk: ^1.1.0` + `flutter pub get` + `cd ios && pod install` | Yes | `1.0.0` has no IAM API (`triggerIAMEvent` → "no such method"). |
| `platform :ios, '15.0'` in `ios/Podfile` (and the `Runner` deployment target) | Yes (iOS) | The plugin and the transitive `PushEngage 1.1.0` pod require iOS 15.0; anything lower fails at `pod install` (KI-F013 / FLUTTER-AUDIT-15 / FLUTTER-BP-12). Apps that must keep iOS 12–14 stay on plugin `1.0.0` (no IAM). |
| `PushEngage.setAppId(...)` in `main()` | Yes (already part of push) | IAM syncs as soon as the App ID is set. No push subscription, no permission. |
| Android: manifest / `MainActivity` / `Application` changes | No | None. The plugin hands the already-resumed activity to the SDK itself. Do NOT forward `onRequestPermissionsResult`. |
| iOS: `AppDelegate.swift` changes | No | The plugin registers the native custom-action handler itself. Don't call `setIAMCustomActionHandler` from Swift — it would overwrite the plugin's handler and the Dart stream would go silent. |
| iOS optional: `BGTaskSchedulerPermittedIdentifiers` = `com.pushengage.iam.refresh` in `ios/Runner/Info.plist` + Background Modes → Background fetch on `Runner` | Optional | Background campaign refresh. Both or neither; without them campaigns refresh on app open. Android needs nothing. |

## API

Two members plus one model, all exported from the package barrel (`import 'package:pushengage_flutter_sdk/pushengage_flutter_sdk.dart';`).

### `triggerIAMEvent` — report a custom trigger event

```dart
Future<void> reportAbandonedCart() async {
  final PushEngageResult<String?> result = await PushEngage.triggerIAMEvent(
    'cart_abandoned',
    {'cart_value': 120, 'currency': 'USD'},
  );

  if (!result.isSuccess) {
    debugPrint('Failed to trigger in-app message: ${result.error}');
  }
}
```

- Signature: `static Future<PushEngageResult<String?>> triggerIAMEvent(String eventName, [Map<String, dynamic>? parameters])` — `parameters` is a positional optional.
- Success `data` is the native message string (`"In-app message event triggered successfully"`). It means the event was **accepted**, not that a message was displayed.
- Empty name → `failure` whose `error` is a `PlatformException` with code `400`, message `Event name is required`.
- Pass only `String`, `num` or `bool` values. They are stringified natively before matching (`2` matches a condition authored as `2`); Android silently drops `null` values. Other value types are handled differently per platform (Android uses `toString()`, iOS drops the key) — don't rely on them. Have numeric dashboard conditions typed `number` (XP-BP-08).
- Campaigns with an **app open** trigger need no call — the native SDK fires them once per process.

### `onIAMCustomAction` — receive `custom` button taps

```dart
class _MyAppState extends State<MyApp> {
  late final StreamSubscription _deepLinkSub;          // push taps (init-code.md)
  StreamSubscription<IAMCustomAction>? _iamActionSub;  // in-app custom actions

  @override
  void initState() {
    super.initState();
    _deepLinkSub = PushEngage.deepLinkStream.listen(_onDeepLink);
    _iamActionSub = PushEngage.onIAMCustomAction.listen((action) {
      // parameters['action'] is the button's "Action name" from the dashboard — route on it.
      // action.actionId is the button's internal key (e.g. "t04B05"), generated by the dashboard.
      switch (action.parameters['action']) {
        case 'view_cart':
          navigatorKey.currentState?.pushNamed('/cart');
          break;
        case 'apply_coupon':
          applyCoupon(action.parameters['code']);
          break;
      }
    });
  }

  @override
  void dispose() {
    _iamActionSub?.cancel();   // FLUTTER-BP-11
    _deepLinkSub.cancel();     // FLUTTER-BP-08
    super.dispose();
  }
  // ...
}
```

- `static Stream<IAMCustomAction> get onIAMCustomAction` — broadcast stream; the first access lazily wires the method-channel handler. No enable/disable call.
- `IAMCustomAction({required String actionId, required Map<String, String> parameters})` — `parameters` values are always `String`. **Route on `action.parameters['action']`** (the dashboard Action name); `actionId` is a dashboard-generated internal key — never switch on it.
- Subscribe in a long-lived widget (the root is simplest, next to the `deepLinkStream` listener) and cancel in `dispose()` (FLUTTER-BP-11). Unlike push taps, there is **no cold-boot buffering** — by design, a button tap can't happen before Dart is up — so timing is not a correctness issue here, only lifecycle hygiene.
- Only `custom` buttons arrive here. `open_url` (http/https only, opened externally), `dismiss`, and `request_notification_permission` are handled natively. A `url` parameter on a `custom` action is **not** opened for you — for in-app navigation, put the route in a parameter and navigate here (XP-BP-09). IAM taps never arrive on `deepLinkStream`.
- Nothing listening → the tap still counts as a click and the message still closes.

## Verification

1. Customer creates and publishes an **app-open** campaign (with a Dismiss button) on the dashboard for the platform's site (one site per platform — the App ID passed to `setAppId` decides which campaigns sync).
2. Run a debug build with `PushEngage.enableLogging(true)` (kDebugMode-gated). iOS simulator is fine — IAM does not need APNs; Android emulator without Play Services is fine too.
3. **Force-quit and relaunch** (app-open fires once per process).
4. The message appears; Dismiss closes it.
5. For a custom-trigger campaign: call `triggerIAMEvent('<exact dashboard event>')` from a debug button; the Dart log shows the `PushEngage#triggerIAMEvent` method-channel marker and the native logs show the eligibility lines.

If nothing appears → run `audit-checks.md` (FLUTTER-AUDIT-14/15), then `../pushengage-debug/diagnostic-tree.md` Branch 8 with the native rejection lines (`../pushengage-debug/log-readers.md` → In-App Messaging).

## Flutter gotchas

- **Two sites, two campaign sets.** A cross-platform app has separate iOS and Android sites; a campaign published on one does not show on the other platform.
- **`^1.1.0` is the floor.** On `^1.0.0` the pub resolver may keep `1.0.0` and `triggerIAMEvent` is a missing method (FLUTTER-AUDIT-01).
- **`pod install` after the bump**, as always (FLUTTER-BP-09) — and raise the Podfile platform to 15.0 first, or `pod install` itself fails.
- **Success ≠ shown.** Treat `isSuccess` as "event accepted"; whether a message displays depends on sync, trigger match, date window, cap and audience.
- **App-open fires once per process**, on both platforms.
- **Subscriber-data audience rules** need a push subscription; device-data rules work everywhere.

## Edit posture

- `pubspec.yaml`, `ios/Podfile` (platform line), `ios/Runner/Info.plist` — auto-edit + announce.
- Background fetch capability on `Runner` — customer-driven (Xcode UI).
- `lib/main.dart` / root widget (stream subscription) and `triggerIAMEvent` call sites — diff + confirm.
- Do NOT touch `AppDelegate.swift`, `MainActivity.kt`, or `AndroidManifest.xml` for IAM.
