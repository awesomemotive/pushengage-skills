# iOS — In-App Messaging (IAM)

Available from iOS SDK **`1.1.0`** (the pinned baseline in `version-matrix.md`). Cross-platform semantics — triggers, audience, action types, frequency caps, troubleshooting — live in `../pushengage/in-app-messaging.md`; read that first if the customer's question is about *behavior* rather than iOS code.

## What IAM needs on iOS

| Item | Required? | Notes |
|---|---|---|
| `pod 'PushEngage', '1.1.0'` / SPM `PushEngage` product at tag `1.1.0` | Yes | IAM lives in the existing app module. **No new pod, no new SPM product.** NSE/NCE targets (`PushEngageExtension`) have no IAM. |
| Deployment target **iOS 15.0+** | Yes | `1.1.0` raised the floor from 12.0 to 15.0 (KI-009 / IOS-BP-17). Apps that must keep iOS 12–14 stay on `1.0.0` without IAM. |
| `setAppID(id:)` + `setInitialInfo(for:with:)` in `application(_:didFinishLaunchingWithOptions:)` | Yes (already part of the push integration) | Nothing else. No push subscription, no notification permission. `setInitialInfo` must run **synchronously inside** `didFinishLaunching` (IOS-BP-14) — SwiftUI apps need `@UIApplicationDelegateAdaptor` (the templates in `init-code.md` already do this). |
| `BGTaskSchedulerPermittedIdentifiers` = `com.pushengage.iam.refresh` + Background Modes → **Background fetch** | Optional | Lets campaigns refresh in the background (opportunistic, ~6 h earliest). **Both or neither** (IOS-BP-15). Without them the SDK logs one line at launch and refreshes on app open only. |
| `PushEngageResources.bundle` | Automatic with CocoaPods / SPM | Ships the IAM Core Data model. Only manual/static-framework integrations copy it themselves (KI-011). |

Nothing about swizzling vs manual mode changes. `PushEngageInAppEnabled` in Info.plist is the *push* URL-in-WKWebView flag (see `init-code.md`) — it is **not** an IAM switch; don't describe it as one.

## Optional: background campaign refresh

Auto-edit + announce posture for the Info.plist key; the capability toggle is customer-driven (Xcode UI).

```xml
<key>BGTaskSchedulerPermittedIdentifiers</key>
<array>
    <string>com.pushengage.iam.refresh</string>
</array>
```

Then Signing & Capabilities → Background Modes → check **Background fetch**. If the customer already has `UIBackgroundModes` in Info.plist, add `fetch` to that array.

Only recommend this if the customer wants campaigns created while the app is closed to be ready on next open without a sync delay; most integrations are fine with refresh-on-open. It does not enable "Remote notifications" — IOS-BP-03 still applies to that mode.

## API

Two methods and one typealias. Everything else IAM-related in the module (`IAMController`, `IAMPosition`, …) is `internal` — never reference it.

### `triggerIAMEvent` — report a custom trigger event

```swift
PushEngage.triggerIAMEvent(
    eventName: "cart_abandoned",
    parameters: ["cart_value": 120, "currency": "USD"]
) { success, error in
    if !success {
        print("Trigger failed: \(error?.localizedDescription ?? "")")
    }
}
```

```objectivec
[PushEngage triggerIAMEventWithEventName:@"cart_abandoned"
                              parameters:@{@"cart_value": @120, @"currency": @"USD"}
                       completionHandler:^(BOOL response, NSError * _Nullable error) {
    if (!response) {
        NSLog(@"Trigger failed: %@", error.localizedDescription);
    }
}];
```

- Signature: `triggerIAMEvent(eventName: String, parameters: [String: Any]? = nil, completionHandler: ((_ response: Bool, _ error: Error?) -> Void)?)`. `parameters` defaults to `nil` in Swift; `completionHandler` has **no default** — pass `nil` explicitly if unused. Obj-C callers pass all three.
- `success == true` means the event was **accepted**, not that a message was displayed. Empty `eventName` → `(false, "Event name is required")`.
- Not gated on subscription, permission, or site status. Call it from anywhere after `setAppID` has run.
- Campaigns with an **app open** trigger need no call — the SDK fires them once per process.
- Pass numbers as numbers (`120`, not `"120"`) and have the dashboard condition typed `number`; values are stringified before matching either way (XP-BP-08).

### `setIAMCustomActionHandler` — receive `custom` button taps

```swift
PushEngage.setIAMCustomActionHandler { [weak self] actionId, parameters in
    // parameters["action"] is the button's "Action name" from the dashboard — route on it.
    // actionId is the button's internal key (e.g. "t04B05"), generated by the dashboard.
    switch parameters["action"] {
    case "view_cart":
        self?.router.push(.cart)
    case "apply_coupon":
        self?.cart.apply(coupon: parameters["code"])
    default:
        break
    }
}
```

```objectivec
[PushEngage setIAMCustomActionHandler:^(NSString *actionId,
                                        NSDictionary<NSString *, NSString *> *parameters) {
    NSString *action = parameters[@"action"];   // dashboard Action name — route on this, not actionId
    if ([action isEqualToString:@"view_cart"]) {
        [self showCart];
    } else if ([action isEqualToString:@"apply_coupon"]) {
        [self applyCoupon:parameters[@"code"]];
    }
}];
```

- Type: `public typealias PEIAMCustomActionHandler = (_ actionId: String, _ parameters: [String: String]) -> Void`. Parameter values are always strings. **Route on `parameters["action"]`** (the dashboard Action name); `actionId` is a dashboard-generated internal key like `"t04B05"` — never switch on it.
- **Single slot.** A second call replaces the first; there is no getter and no removal. Register it **once, in the AppDelegate** right after `setInitialInfo`, and dispatch to the app's router from there (IOS-BP-16). Registering from a view controller's `viewDidLoad` overwrites the app-level handler and the closure is retained for the process lifetime — capture `[weak self]`.
- Only `custom` buttons arrive here. `open_url`, `dismiss`, `request_notification_permission` are handled by the SDK. A `url` parameter on a `custom` action is **not** opened for you — if the customer wants an in-app deep link, put the route in a parameter and open it in this handler (XP-BP-09). IAM taps never reach `setNotificationOpenHandler`.
- No handler registered → the tap still counts as a click and the message still closes.

Where it goes in the swizzling template from `init-code.md` (diff + confirm posture — this is AppDelegate code):

```swift
func application(_ application: UIApplication,
                 didFinishLaunchingWithOptions launchOptions:
                 [UIApplication.LaunchOptionsKey: Any]?) -> Bool {
    PushEngage.setAppID(id: "<APP_ID_UUID_FROM_DASHBOARD>")
    PushEngage.setInitialInfo(for: application, with: launchOptions)
    PushEngage.setIAMCustomActionHandler { actionId, parameters in
        // route on parameters["action"] (dashboard Action name); parameters are [String: String]
    }
    #if DEBUG
    PushEngage.enableLogging = true
    #endif
    return true
}
```

## How messages are presented (why SwiftUI just works)

The SDK presents the message in its **own `UIWindow`** above the app's windows, not inside the host view hierarchy. So UIKit, SwiftUI (`App` lifecycle with a delegate adaptor), and multi-scene apps all behave the same; no view-hierarchy hooks, no `.sheet` conflicts. There is no swipe-to-dismiss on iOS and no SDK-drawn close button; tap-outside dismissal only when the campaign enables it.

## Verification

1. Customer creates and publishes an **app-open** campaign (any position, with a Dismiss button) on the dashboard.
2. Build to a device or simulator (IAM does not need APNs, so the simulator is fine), with `enableLogging = true`.
3. **Force-quit and relaunch** the app (app-open fires once per process — backgrounding is not enough).
4. The message appears; tapping the Dismiss button closes it.
5. For a custom-trigger campaign: call `triggerIAMEvent(eventName:)` with the exact dashboard event name from a debug button and confirm the message appears.

If nothing appears → `../pushengage-debug/diagnostic-tree.md` Branch 8, with the per-campaign rejection lines from the console (`../pushengage-debug/log-readers.md` → In-App Messaging).

## iOS gotchas

- **Config is cached.** The SDK caches site key and environment from the first `setAppID` / `setEnvironment`. After changing either, terminate and relaunch.
- **App-open fires once per process.** Returning from background does not re-show. Only a fresh launch does.
- **Errors go to `os_log`, info to stdout.** With `enableLogging` on, per-campaign evaluation lines print to the Xcode console, but sync HTTP failures are error-level `os_log` — capture both (see `log-readers.md`).
- **Half-configured background refresh** (plist key without Background fetch, or vice versa) just logs one line at launch and falls back to refresh-on-open. Not a crash; not a reason IAM "doesn't work" (KI-010).
- **`open_url` is http(s) only and external.** Custom schemes are refused. Use a `custom` action for in-app navigation.
- **Queue cap of 10** eligible messages; lower `priority` number shows first.
- **Subscriber-data audience rules need a real push subscription** (APNs token), so a simulator or a build without push entitlements will never resolve them — device-data rules still work.
- No observer for impressions/dismissals; the only host hook is the custom-action handler.

## Edit posture

- `Info.plist` (`BGTaskSchedulerPermittedIdentifiers`, `UIBackgroundModes`) — auto-edit + announce.
- Background fetch capability — customer-driven (Xcode UI). Don't edit `.pbxproj` / entitlements programmatically.
- AppDelegate handler registration and any `triggerIAMEvent` call sites — diff + confirm.
